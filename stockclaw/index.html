StockClaw AI: the data platform

StockClaw turns filings, central-bank releases and news into ranked signals for each user's watchlist. This page is about the data side: bringing dozens of feeds in once, processing them for each user, and keeping each user's data to themselves.

01The problem

Each user follows their own watchlist of tickers. The obvious design crawls every source for every user, so the number of external calls grows with users times tickers, and the sources that matter most, such as the SEC, publish strict limits on how fast you may call them.

The sources are also untidy. The same story arrives from several feeds, an SEC filing appears in two places, a feed host can stop answering in the middle of a request, and a commercial news feed may not allow the use you have in mind.

02How the data moves

The scheduler runs the crawl every 20 minutes. It builds the union of every user's watchlist tickers from Postgres, runs each crawler once, and turns every item into a validated record whose ID is a hash of its URL and title, or the accession number for an SEC filing. A separate poller checks the SEC's latest-filings feed every 5 minutes on weekdays and keeps what it finds in Redis for 26 hours, so the main crawl can pick it up.

The sources are SEC filings and insider forms, the Federal Reserve, ECB, Bank of Japan and Bank of England, US federal agencies, official data APIs such as BLS, Treasury, World Bank and Eurostat, press wires, and 33 news and content sources.

03Decisions and trade-offs

Crawl once, fan out per user

Sources are crawled once for the union of all tickers, then one task per user does the filtering and synthesis. External calls grow with the number of distinct tickers, not with users times tickers.

Loads that can be repeated safely

Duplicates are dropped by ID within a cycle, each user only receives IDs they do not already have, and market-wide rows have a unique constraint with insert-or-ignore. A retried task cannot write the same signal twice.

Privacy enforced by the database

Every user table has row-level security. Each request sets the current user and switches to a restricted role before it reads, and system tables have security switched on with no policy at all, so they fail closed.

Polite to the sources

SEC calls are capped at 5 per second across all processes, counted in Redis, and a final refusal pauses every SEC call for 10 minutes. Each US federal host gets at most one request per second.

04Moving vectors into Postgres

The chat assistant first kept its vectors in ChromaDB, which stores data on the local disk of the container that writes it. The worker wrote vectors to its own disk while the web service read from an empty store of its own, so every non-admin question was refused for lack of context.

  • Vectors moved into a side table in the shared Supabase database, keyed to the signal and deleted with it, rather than a column that would travel with every load of a signal.
  • No approximate (HNSW) index. Every search is limited to one user's rows, and an approximate index searches the whole table and filters afterwards, so a user with few rows could get fewer results than asked for, or none. An exact scan on a per-user index is fast at this size.
  • The same row-level security as the signals, and a daily backfill that embeds missing rows 300 at a time.
  • Measured locally: 10,000 rows took 20 MB, and an exact search over one user's rows took 2.9 ms. The decision record says plainly that it had not yet been verified on production when it was written.

05Licences are data quality too

I audited the terms of the 33 news and content sources the system ingested, classed each by whether commercial use is allowed, and paused the social sources by default behind switches. The audit, its data and the decisions that followed are recorded in the repository next to the code.
